# 猫咪单图生成多姿态与动作视频汇报

## 1. 项目目标

本项目目标是基于一张猫咪参考图，生成同一只猫咪的多姿态资产，并进一步生成动作视频。当前重点验证两个动作：

- 吃饭
- 奔跑

理想链路是：

输入一张猫咪图片后，系统自动生成六张不同姿态图，再选择合适姿态生成动作首帧，最后通过图生视频模型生成短视频。后续可以继续扩展喝水、打滚、躺着、挥爪等动作。

## 2. 当前实现方式

当前已完成一条可运行的原型链路，整体分为五个阶段。

第一阶段是参考图输入。用户只需要提供一张猫咪图片，系统会将其作为身份参考，尽量保留猫咪的毛色、脸部花纹、体型和整体风格。

![原始参考图](report_assets/report_original_reference.jpg)

第二阶段是六姿态生成。模型根据参考猫图分别生成坐姿、侧面站姿、趴卧、伸展、抬爪、睡觉等姿态。生成后进行背景去除，得到透明背景姿态图，并汇总为六姿态预览图。

![六姿态生成结果](report_assets/report_six_poses.jpg)

第三阶段是动作首帧生成。对于吃饭视频，首帧不再采用正面视角，而是调整为偏侧视角，让猫咪身体、猫粮碗和低头吃饭动作更加清晰。这个调整能让视频模型更容易生成“正在吃饭”的动作，而不是单纯正面坐着。

![偏侧吃饭首帧](report_assets/report_side_eat_keyframe.jpg)

第四阶段是图生视频。以动作首帧作为输入，生成吃饭和奔跑短视频。吃饭动作使用猫粮碗作为明确动作锚点；奔跑动作使用侧面姿态作为输入，让四肢运动方向更明确。

第五阶段是后处理。视频生成后统一做裁切、补边、转码和帧率处理，使输出更适合后续展示和合成。

## 3. 当前验证结果

本次验证说明链路已经具备基本可用性：

- 单张参考图可以触发完整生成流程
- 六张姿态图可以自动生成并去背景
- 偏侧吃饭首帧能够生成，并且构图方向符合预期
- 吃饭和奔跑视频均可生成
- 视频可以统一后处理为固定规格
- ComfyUI 中已封装为可复用节点，便于后续继续迭代

不过，当前结果还不能作为稳定生产链路直接使用。核心问题集中在身份保持和姿态稳定性上。

## 4. 跑偏问题记录

本轮实验中，部分姿态图出现了跑偏。主要表现为脸部花纹过度变化、灰色面罩被强化、眼睛和身体比例不稳定，以及动作姿态与预期不完全一致。

以下是本轮比较明显的跑偏样例：

![跑偏姿态样例](report_assets/report_drift_examples.jpg)

其中，第一张脸部灰色区域过重，和参考猫的身份特征不够一致；第四张动作姿态不够准确，未稳定表达预期的伸展动作；第五张虽然具备抬爪动作，但脸部、眼睛和花纹仍有漂移。

由于视频生成依赖首帧或姿态图，一旦上游姿态图已经跑偏，视频阶段会继续放大这些问题。尤其是奔跑这类大动作，对身体结构、四肢位置和连续运动要求更高，因此更容易出现比例漂移或动作不自然。

## 5. 跑偏原因分析

首先，六张姿态图是分别生成的。模型每次都会重新理解“同一只猫”的身份特征，因此不同姿态之间容易出现脸型、花纹、眼睛颜色和身体比例变化。

其次，当前身份约束主要依赖提示词。提示词可以描述“同一只猫”和具体外观特征，但它不是强约束。模型仍然会优先追求“可爱”“毛绒”“3D 卡通”等风格效果，从而弱化参考图中的具体身份。

第三，姿态生成缺少结构控制。当前没有使用轮廓、深度、姿态草图或遮罩来固定动作结构，模型自由发挥空间较大，所以伸展、抬爪、奔跑这类动作容易偏离预期。

第四，视频模型会放大首帧问题。图生视频模型通常强依赖输入首帧，如果首帧里的体型、花纹或角度已经不够稳定，视频生成过程中很容易继续漂移。

## 6. 后续改进方向

### 6.1 引入多候选机制

每个姿态不应只生成一张图。后续建议每个姿态生成多张候选，再进行筛选。只有通过筛选的姿态图才进入动作首帧和视频生成阶段。

这样可以显著降低单次随机生成失败对整条链路的影响。

### 6.2 增加质量筛选

需要建立明确的质量筛选标准，包括：

- 是否仍然像同一只猫
- 脸部花纹是否稳定
- 眼睛颜色和大小是否一致
- 身体比例是否接近参考图
- 是否只有一只猫
- 是否全身完整
- 是否没有多余道具、文字和水印

跑偏结果应单独归档，不进入正式展示结果。

### 6.3 强化身份保持

后续需要引入比提示词更强的身份保持方案，例如：

- 多参考图输入
- 参考图适配器
- 图像身份特征约束
- 针对这只猫训练轻量 LoRA
- 使用本地图像编辑模型配合身份保持模块

其中，训练猫咪专属 LoRA 或使用稳定的参考图适配器，是提升一致性的关键方向。

### 6.4 增加结构控制

姿态图生成阶段建议加入轮廓、深度、姿态草图或遮罩控制。这样可以让模型在保持角色身份的同时，按照预设结构生成动作。

对于奔跑、伸展、抬爪这类动作，结构控制比单纯提示词更可靠。

### 6.5 优化吃饭动作首帧

吃饭视频已经验证出偏侧视角更好。后续应继续固定这个方向：

- 猫咪保持三分之四侧面
- 猫粮碗放在嘴前偏侧位置
- 猫嘴接近猫粮
- 保持全身完整
- 背景保持干净

首帧通过筛选后，再进入视频生成阶段。

### 6.6 视频多次生成取优

同一个动作首帧建议生成多个视频候选，再选动作最稳定的一版。尤其是奔跑动作，建议至少生成多次候选，因为腿部运动和身体比例更容易不稳定。

筛选重点包括动作是否明确、身体是否出画、身份是否漂移、四肢是否合理、画面是否闪烁。

### 6.7 切换到完全本地开源链路

后续目标是将云端 API 原型替换为完全本地开源模型链路。图像侧可采用 Qwen-Image / Qwen-Image-Edit 方向，视频侧可采用 Wan2.2 本地权重。

本地化后可以获得更强的可控性，包括采样参数、模型组合、结构控制、LoRA、质量筛选和批量生成策略。但前提是需要完成 CUDA 版环境、模型权重、ComfyUI 工作流和显存优化方案。

## 7. 阶段结论

当前链路已经验证了整体可行性：单图输入、多姿态生成、动作首帧生成、图生视频和后处理均已跑通。吃饭动作通过调整为偏侧视角，动作表达明显更清楚。

当前最大问题不是视频模型是否能生成，而是上游姿态图和首帧的一致性控制不足。后续重点应从“能生成”转向“稳定生成同一只猫”，也就是引入多候选、质量筛选、身份保持和结构控制。

当六姿态图质量稳定后，吃饭、奔跑以及后续喝水、打滚、躺着等动作都可以复用同一套动作视频生成框架继续扩展。

## 8. 后续本地开源模型运行配置

如果后续不再调用云端 API，而是完全使用本地开源模型，需要重点考虑显存、内存、硬盘和推理速度。视频模型的硬件压力远高于图片模型，因此建议先以视频模型需求作为服务器配置基准。

### 8.1 最小验证配置

适合目标：验证本地开源模型能否跑通，不追求速度和稳定批量生产。

| 配置项 | 建议 |
| --- | --- |
| GPU | RTX 4090 24GB 或同级 24GB 显存 GPU |
| 内存 | 64GB 起步，建议 128GB |
| 硬盘 | 1TB NVMe 起步 |
| 系统 | Linux 优先，Windows 可用于验证但部署复杂度更高 |
| 适合模型 | Wan2.2-TI2V-5B、Qwen-Image-Edit 量化或 offload 方案 |

Wan2.2 官方说明中，TI2V-5B 在 720P 场景下可通过 offload 等方式在 24GB 显存 GPU 上运行。因此 24GB 显存可以作为本地验证的起步线。

### 8.2 推荐研发配置

适合目标：稳定调试 ComfyUI 工作流、批量生成候选图、进行小规模视频测试。

| 配置项 | 建议 |
| --- | --- |
| GPU | RTX 4090 24GB，或 L40S 48GB |
| 内存 | 128GB |
| 硬盘 | 2TB NVMe |
| 系统 | Ubuntu Server / Ubuntu Desktop |
| 适合模型 | Wan2.2-TI2V-5B、本地图像编辑模型、LoRA、ControlNet |

这个配置更适合做“多候选生成 + 人工筛选 + 少量视频生成”的研发流程。若使用 24GB 显存，建议优先使用 5B 视频模型，配合 FP8、GGUF、CPU offload、分块 VAE 等优化。

### 8.3 生产级配置

适合目标：稳定运行高质量图生视频，减少等待时间，支持多人或批量任务。

| 配置项 | 建议 |
| --- | --- |
| GPU | A100 80GB、H100 80GB，或多卡 L40S / A100 |
| 内存 | 256GB 起步 |
| 硬盘 | 2TB-4TB NVMe |
| 系统 | Linux Server |
| 适合模型 | Wan2.2-I2V-A14B、Wan2.2-TI2V-5B、多候选批处理 |

Wan2.2 官方说明中，I2V-A14B 单卡推理建议至少 80GB 显存；如果要高质量、稳定、减少 OOM，生产环境建议直接按 80GB 显存级别规划。

## 9. API 调用价格与成本估算

价格会随模型版本、部署地域和官方策略变化，以下按当前官方价格页做参考，实际以阿里云百炼控制台为准。

### 9.1 当前原型链路涉及的 API

当前 API 原型主要消耗两类资源：

| 环节 | 模型 | 计费方式 |
| --- | --- | --- |
| 姿态图和动作首帧生成 | Qwen 图像编辑模型 | 按成功输出图片张数计费 |
| 吃饭 / 奔跑视频生成 | Wan 图生视频模型 | 按成功输出视频秒数计费 |

阿里云百炼官方价格页说明，图像生成按成功输出张数计费，失败不计费；视频生成按输出视频秒数计费。

### 9.2 单次基础链路成本

以当前原型为例，单次生成包含：

- 六张姿态图
- 两张动作首帧
- 两段 5 秒视频

也就是约 8 张图片和 10 秒视频。

| 项目 | 单价参考 | 数量 | 估算费用 |
| --- | --- | --- | --- |
| 图像编辑 | qwen-image-edit 国际部署约 $0.045/张 | 8 张 | 约 $0.36 |
| 视频生成 | wan2.2-i2v-flash 720P 国际部署约 $0.036/秒 | 10 秒 | 约 $0.36 |
| 合计 |  |  | 约 $0.72/次 |

如果使用中国内地部署，图像编辑模型 qwen-image-edit 参考价约 $0.043/张。部分视频模型在不同地域的可用型号和价格不同，需要以控制台实际显示为准。

### 9.3 多候选优化后的成本

为了解决跑偏问题，后续建议使用多候选生成。成本会随候选数量线性增加。

示例方案：

- 每个姿态生成 4 个候选，共 24 张姿态图
- 吃饭和奔跑各生成 4 个动作首帧，共 8 张首帧
- 每个动作生成 3 个视频候选，共 30 秒视频

| 项目 | 数量 | 国际部署估算 |
| --- | --- | --- |
| 图像编辑 | 32 张 | 约 $1.44 |
| 视频生成 | 30 秒 | 约 $1.08 |
| 合计 |  | 约 $2.52/组 |

这个成本换来的是更高稳定性：通过多候选和质量筛选，可以显著减少“单次跑偏导致整组不可用”的情况。

### 9.4 本地开源与 API 的成本取舍

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 继续调用 API | 部署快、成功率高、不占本地显卡 | 按量计费，批量生成成本会增长 |
| 本地开源模型 | 长期可控、可训练 LoRA、可深度优化工作流 | 前期硬件成本高，部署复杂，调参周期长 |

短期建议继续使用 API 做产品验证和效果迭代；当动作类型、质量标准和生成规模稳定后，再评估是否购置本地服务器或租用 GPU 云服务器部署开源模型。
